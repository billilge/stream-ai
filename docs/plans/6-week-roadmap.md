# 슬랑제 발표까지 6주 로드맵

> 작성일: 2026-09-15
> 수정일: 2026-09-20 (사물함 범위 편입, 1주차 3번 태스크 조정, `chunk.py` 담당 정정, 2주차 태스크 구체화)
> 기간: 2026-09-15 ~ 2026-10-26
> 목표: 슬랑제에서 시연 가능한 상태
> 인원: 2명 / 주당 10~20시간
> 참고: `docs/reference/db-schema.md` (백엔드 DB 스키마)

> **이 문서는 `10-week-roadmap.md`로 승계됐다(2026-09-28).**
> 발표일이 11/21로 확정되고 배포·API 연결이 범위에 들어와 기간과 순서가 모두 바뀌었다.
> 1~2주차 기록은 여기 남기고, 3주차부터는 새 문서를 본다.

8주 로드맵(`8-week-roadmap.md`)을 6주로 줄이고 순서를 다시 잡았다.
계획은 바뀐다. 바뀌면 이 파일을 고치고 왜 바꿨는지 커밋 메시지에 남긴다.

## 순서

| 단계 | 내용 | 데이터 출처 |
| --- | --- | --- |
| 1 | 고정 정보 답변 + 말투 교정 | `docs/seed/` (직접 작성) |
| 2 | 학생회 공지·행사 답변 | 시드 → 백엔드 API (`notices`, `events`) |
| 3 | 빌릴게 재고·사물함 잔여 실시간 조회 | 가짜 API → 백엔드 API (`items.count`, `lockers`) |
| 4 | 학교 공지 링크 안내 | 학교 홈페이지 공지 목록 수집 |

말투 교정은 프롬프트 파일만 고치는 일이라 1주차에 초안을 만든다.
확인 질문 10개에서 v2가 나아서 1주차에 바로 적용했다.
다만 말투를 고치다 "모르면 모른다고 답하기"가 약해질 수 있어서, 2주차 골든셋 점수로 v1과 다시 비교하고 떨어지면 되돌린다.

학교 공지 목록 수집은 3주차에 당겨서 시작하고, 답변 연결은 5주차에 한다.
별도 허락은 받지 않는다. 대신 robots.txt를 확인하고 목록만 하루 1~2회 가져온다(AGENTS.md 금지 사항).

### 고정 정보는 DB에 없다

간식 행사 장소, 빌릴게 사용 방법처럼 거의 바뀌지 않는 정보다.
`items` 테이블에는 이름·종류·수량만 있고 이용 방법 칸이 없다.
그래서 `docs/seed/`에 문서로 쓰고 `유효기간`은 비워둔다.
프롬프트에 직접 넣지 않는 이유는 출처(제목·게시일·링크)를 똑같이 표시하기 위해서다.

### 사물함은 개인별 항목만 뺀다

처음에는 사물함 전체를 인증이 필요하다는 이유로 제외했다. 1주차에 받은 학생 질문 59건 중
사물함이 10건이어서 뺄 근거가 없어졌다. 다만 사물함 질문은 두 종류로 갈린다.

- **인증이 필요 없다**: 신청 기간·방법, 구역별 잔여 수량.
  잔여 수량은 개인 정보가 아니라 빌릴게 재고와 같은 실시간 데이터고, 신청 기간·방법은 공지에 있으니 문서형이다
- **인증이 필요하다**: "내가 신청한 사물함 위치", "내가 놓치고 있는 일정" 같은 개인별 조회

앞쪽만 6주 범위에 넣는다. 뒤쪽은 인증 헤더가 확정된 뒤로 남긴다(`users.json`도 그때 쓴다).

### 공지가 짧아서 청킹이 거의 일어나지 않는다

2026-09-20에 재보니 실제 카톡 공지가 360자, 목업 공지 12건이 71~230자였다.
AGENTS.md 청킹 규칙은 공지를 500~800자로 자르는데, 이 길이면 창이 한 번도 열리지 않는다.

그래도 기준을 낮추지 않는다. 지금 공지는 "신청 기간", "참가비"처럼 짧은 항목이 나열된
형태라 쪼개면 한 질문에 함께 필요한 항목이 다른 청크로 갈라진다. "참가비 얼마야"에
반쪽만 검색되는 쪽이 더 나쁘다. 긴 공지가 올 때를 위한 안전망으로 남긴다.

대신 짧은 공지에서는 다른 게 문제가 된다. 360자 중 116자(32%)가 "안녕하십니까",
"감사합니다" 같은 인사말·맺음말이었다. 모든 공지에 같은 표현이 들어가면 BM25에서
그 단어들이 변별력을 잃는다. 청킹보다 이 정규화가 먼저다. 2주차에 점수로 확인한다.

### 학교 공지는 내용을 답하지 않는다

제목·게시일·링크만 안내한다(AGENTS.md "학교 공식 정보를 직접 답하지 않는 이유").
그래서 본문은 수집하지 않고 목록만 하루 1~2회 가져온다.
학생회 문서와 섞이지 않게 별도 인덱스로 둔다.

## 주차별 일정

주마다 태스크 3개. 주차는 화요일 시작 기준이다.

### 1주차 (9/15~9/21) — 질문 수집과 준비

1. **학생 질문 40건 수집** (이승빈) — 학생이 쓴 표현 그대로 받는다. 문서는 아직 쓰지 않는다
2. **말투 교정 v2 초안** (이상현) — `prompts/system_v2.md`. 스텁 문서로 확인 질문 10개(답이 없는 질문 3개 포함)를 직접 돌려본다
3. **백엔드 확인 사항 전달 + `chunk.py` 초안** (이상현 → 이승빈 인계) — 응답 모양을 우리끼리 정할 수는 없다.
   서준이 답을 줘야 확정되므로, 물어볼 목록을 `db-schema.md` 5절에 모아 전달한다.
   `chunk.py`의 담당은 AGENTS.md대로 이승빈이다. `sync.py` → `chunk.py` → `build_index.py`가 한 사슬이라
   담당이 갈리면 매주 같은 파일을 함께 고치게 된다. 1주차에 이상현이 초안만 쓰고 2주차부터 이승빈이 이어받는다.
   청킹은 공지 500~800자에 앞뒤 100자 중복, 표는 통째로, 게시일 필수.
   API 필드명과는 무관하다(그 변환은 3주차 `sync.py`가 맡는다)

**완료 기준**: 학생 질문 40건, v2 초안, 백엔드 확인 목록 전달, `chunk.py` 초안

### 2주차 (9/22~9/28) — 고정 정보 답변

1. **고정 정보 시드 문서** (이승빈) — 빌릴게 사용법·행사 장소 등을 `docs/seed/`에 쓴다.
   이상현의 재분류 결과를 받고 시작한다. 문서형으로 재분류된 질문이 이 문서가 답해야 할 질문이다
2. **BM25 인덱스 + `search.py` 실제 구현** (이승빈) — `build_index.py`로 인덱스를 만들고 스텁을 교체한다.
   **주 중반까지 필요하다.** 이게 없으면 이상현이 Recall@5를 잴 수 없다.
   반환 모양은 새로 합의하지 않는다. AGENTS.md "모듈 경계"와 `db-schema.md` 68행(`doc_id = {table}-{pk}`)을 따른다.
   `chunk.py`를 이어받아 인사말·맺음말 정규화를 넣고 넣기 전후 점수를 비교한다.
   `_is_rule` 수정은 PR #10에서 이미 반영됐다
3. **골든셋 78건 + `eval.py` + v1/v2 비교** (이상현) — 함정 20건 포함. 세 덩어리다.
   (a) `test_data/test_cases.json` 59건을 `eval/golden.jsonl`로 옮기면서 `source` 라벨을
   AGENTS.md "데이터 분류" 4종 기준으로 다시 매긴다. 지금 59건 중 44건이 `API`인데 "빌릴게 설치 방법",
   "대여시간 안내", "행사 장소"처럼 실제로는 문서형인 것이 섞여 있다. 서비스가 아니라 질문 단위로 가른다.
   (b) 답이 없는 함정 19건을 새로 쓴다. 기존 59건에 "모르겠습니다"가 정답인 문항은 1건뿐이다.
   `must_not` 8건은 오답 방지라 함정과 다른 지표로 센다.
   (c) `eval.py`를 쓰기 전에 `app.py`의 프롬프트 조립을 함수로 분리해 `today`를 주입할 수 있게 한다.
   지금은 `relay()` 안에서 현재 시각을 직접 계산해 밖에서 고정할 수 없고, 그대로 두면 실제 코드와
   다른 프롬프트를 평가하게 된다. 평가 기준 시각은 `test_cases.json`의 `reference_now`(2026-09-19)로 맞춘다

**완료 기준**: "빌릴게 어떻게 써요?"에 출처 달린 답변, 1차 점수표, 프롬프트 버전 확정

**2주차에 잴 수 있는 범위**: 골든셋 전체가 아니다. API 조회는 3~4주차, 링크 안내는 5주차라
그 케이스들은 아직 돌릴 수 없다. 재분류 후 RAG 케이스와 함정 20건만 1차 점수에 들어간다.
프롬프트 버전 판단은 Recall@5가 아니라 **함정 정답률과 답변 채점**으로 한다.
검색 점수는 프롬프트를 바꿔도 변하지 않는다

### 3주차 (9/29~10/5) — 학생회 공지·행사

1. **가짜 공지·행사 API** (이승빈) — 실제 API와 같은 모양으로 응답한다. 필드명은 camelCase(`noticeId`, `applyEndAt`),

**완료 기준**: 삭제·지난 공지를 거르고 최신 공지로 답한다. 학교 공지 목록이 쌓인다

## DB 스키마에서 나온 제약

자세한 내용은 `docs/reference/db-schema.md`.

- **삭제 필터**: `notices`, `events`는 `is_deleted = 1`인 행을 인덱싱하지 않는다
- **공지에 유효기간이 없다**: `created_at`만 있다. 제목·본문에서 "2026-2학기" 같은 표현을 뽑고,
  오래된 공지는 답변에 경고를 붙인다
- **행사 유효기간**: `apply_end_at`(신청 마감), `event_end_at`(행사 종료)을 쓴다.
  "지금 신청 가능?"은 `recruit_status`보다 `apply_end_at`과 현재 시각 비교가 안전하다
- **재고는 인덱싱 금지**: `items.name`은 검색 대상, `items.count`는 실시간 조회만
- **첨부파일은 파싱하지 않는다**: 링크로만 안내한다
- **동기화는 전체 재구축**: 스키마 문서는 `updatedAfter` 증분 동기화를 제안하지만,
  AGENTS.md대로 매번 전체를 다시 만든다. 삭제가 자동으로 반영되어 더 단순하다

## 확인할 것

백엔드(서준)에 물어볼 것은 `docs/reference/db-schema.md` 5절로 모았다.
두 군데에 나뉘어 있으면 한쪽만 갱신되어 어긋난다. 여기는 나머지만 남긴다.

- [ ] (프론트) 공지·행사 상세 페이지 주소 형식. 출처 링크를 만들 때 필요하다
- [ ] (학교) robots.txt에서 공지 목록 경로 허용 여부, RSS 제공 여부
- [ ] (공동) 학교 공지 수집 파일 이름과 담당

골든셋은 78건(함정 20 포함)이다. 학생에게 직접 받은 59건을 버리지 않고 함정 19건을 더한 수다.
AGENTS.md는 100~150건을 기준으로 두지만 이 일정에서는 78건으로 간다. 함정 20개는 줄이지 않는다.
